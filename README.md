# Инференс LLM на vLLM в Kubernetes (только CPU)

Тестовое задание на позицию Data Engineer (стажёр), команда исследования технологий машинного обучения.

Модель `Qwen/Qwen2.5-1.5B-Instruct` работает на vLLM 0.32.0 в Minikube, строго на CPU, из rootless-образа. Веса скачиваются в PVC один раз, настройки живут в ConfigMap, токены в Secret, а промпты и ответы модели не попадают в логи. Бонусы 1, 2 и 3 выполнены.

Все требования проверяются одной командой: [`scripts/verify_deployment.py`](scripts/verify_deployment.py).

## Запуск

Нужны Docker, kubectl, Minikube и Python 3.11+. Модели хватает 12 ГБ RAM и 10 CPU в Minikube. Диск: 5 ГБ под образы, 3 ГБ под веса.

**1. Кластер и образы**

```bash
minikube start --driver=docker --cpus=10 --memory=12g
```

```bash
docker build -f docker/model-downloader/Dockerfile -t vllm-model-downloader:1.0.0 .
```

```bash
docker build -f docker/vllm/Dockerfile -t vllm-cpu-private:0.32.0 .
```

```bash
minikube image load vllm-model-downloader:1.0.0
```

```bash
minikube image load vllm-cpu-private:0.32.0
```

**2. Секреты**

```bash
cp k8s/overlays/minikube/secrets.env.example k8s/overlays/minikube/secrets.env
```

В `secrets.env` впишите `VLLM_API_KEY` (например, из `openssl rand -hex 32`). `HF_TOKEN` нужен только для закрытых моделей. Файл в `.gitignore`.

**3. Деплой**

```bash
kubectl apply -k k8s/overlays/minikube
```

```bash
kubectl -n vllm rollout status deployment vllm --timeout=15m
```

Первый запуск занимает около 5,5 минуты: примерно 2 минуты на скачивание, 1 минута на компиляцию, 2 минуты на прогрев. Следующие запуски обходятся без скачивания.

**4. Запрос к модели**

```bash
kubectl -n vllm port-forward svc/vllm 18000:8000
```

```bash
curl http://127.0.0.1:18000/v1/chat/completions \
  -H "Authorization: Bearer $VLLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen2.5-1.5b-instruct", "messages": [{"role": "user", "content": "Привет!"}], "max_tokens": 32}'
```

**5. Проверка всех требований**

```bash
python scripts/verify_deployment.py
```

Unit-тесты фильтра не требуют кластера:

```bash
python -m pytest tests
```

**Изменение настроек.** Отредактируйте [`k8s/base/vllm-config.yaml`](k8s/base/vllm-config.yaml) или [`k8s/base/vllm.properties`](k8s/base/vllm.properties) и снова выполните `kubectl apply -k`. Kustomize добавляет к имени ConfigMap хеш содержимого, поэтому Deployment перезапустится сам, без пересборки образа.

**Другая модель.** Поменяйте `MODEL_ID`, `MODEL_REVISION` и `MODEL_DIR` в `vllm.properties`.

**Процессоры без AVX-512.** Значения `dtype` и `VLLM_CPU_*` подобраны под Ryzen 7500F (Zen 4). На других CPU работают те же манифесты, но цифры скорости будут другими.

## Приватность логов

Перед реализацией я прошёл по исходникам vLLM 0.32 и нашёл больше путей утечки, чем `--enable-log-requests`:

| Путь утечки | Что попадает в лог | Что делает фильтр |
|---|---|---|
| `RequestLogger`, INFO | Текст ответа, параметры запроса со `stop` и `logit_bias` | Оставляет ID, `max_tokens`, `temperature`, `top_p`, `finish_reason` |
| `RequestLogger`, DEBUG | Промпт и всё тело запроса | Отбрасывает |
| `Request %s failed: %s`, INFO | Текст исключения, который может цитировать ввод | Оставляет только тип исключения |
| `Error with model %s`, ERROR | Поле `model` из запроса | Заменяет на `<redacted>` |
| `dump_engine_exception` | Токены всех запросов в батче при сбое движка | Отбрасывает |
| Traceback в `uvicorn.error` | Текст исключения | Оставляет стек и тип, убирает сообщение |
| Access-лог uvicorn | Query string | Отключён, заменён на `AuditLogMiddleware` |

Строка `Error with model` не теоретическая: маркер из проверочного запроса попал именно туда и был отфильтрован.

Почему фильтр, а не патч `site-packages`:

- vLLM применяет конфиг из `VLLM_LOGGING_CONFIG_PATH` в каждом порождённом процессе, поэтому фильтр работает и в API-сервере, и в движке.
- Он не ломается при обновлении vLLM, а патч пришлось бы переносить.
- Правило строится от запрета: в модулях, работающих с контентом, остаются только числа и ID запросов. Новая строка лога в новой версии vLLM будет скрыта по умолчанию.

Пример лога для одного запроса:

```text
INFO [vllm.entrypoints.serve.utils.request_logger] Received request chatcmpl-af6e2d43fe026dba: max_tokens=8 temperature=0.7 top_p=0.8 (content redacted)
INFO [vllm.entrypoints.serve.utils.request_logger] Generated response chatcmpl-af6e2d43fe026dba: finish_reason=length (content redacted)
INFO [vllm.privacy_audit] API request: method=POST path=/v1/chat/completions status=200 duration_ms=56385.3
```

Настройки логирования и middleware заданы в [`entrypoint.sh`](docker/vllm/entrypoint.sh), а не в ConfigMap, чтобы их нельзя было случайно отключить при смене параметров.

## Контроль доступа

Штатный `--api-key` vLLM защищает только пути с префиксами `/v1`, `/v2`, `/inference` и `/cohere`. Инференс через `POST /invocations` и служебные маршруты вроде `/tokenize` и `/metrics` остаются открытыми. Поэтому `RequireTokenMiddleware` требует токен на всех маршрутах, кроме `/health`, который нужен для проб. Он наследует проверку токена в постоянное время из самого vLLM.

Разница проверена на живом сервере. Для контроля тот же под запускался штатной командой `vllm serve` с `VLLM_API_KEY`, но без моего фильтра и middleware:

| Проверка | Штатный vLLM | Это решение |
|---|---|---|
| `/v1/chat/completions` без токена | 401 | 401 |
| `/invocations` без токена | **200, модель сгенерировала ответ** | 401 |
| `/tokenize` без токена | **200** | 401 |
| `/metrics` без токена | **200** | 401 |
| Текст ответа в логах | **`output: 'MARKERupstream16578'`** | Нет |

Все проверки `verify_deployment.py` проходят и при принудительном уровне логирования DEBUG.

## Что выяснилось при развёртывании

- **Имя Service ломает vLLM.** Service с именем `vllm` добавляет в под переменную `VLLM_PORT=tcp://...`, и vLLM падает, приняв её за свою настройку. Решено через `enableServiceLinks: false`.
- **Компилятор нужен в рантайме.** Triton-CPU собирает ядра через `cc`, а `torch.compile` собирает C++. Отключаемого флага для Triton нет, поэтому `g++` есть в образе. Это увеличивает поверхность атаки, но компенсируется read-only корневой ФС и отсутствием capabilities.
- **Первая генерация занимает около 100 секунд.** Пауза не исчезала ни при `-O0`, ни без prepack у zentorch, а один процесс загружал ровно одно ядро. В образе без компилятора запрос упал с `Failed to find C compiler` из Triton, и после этого появился кэш `/tmp/.triton` на 124 МБ: Triton компилирует ядра при первой встрече с новой формой батча. Поэтому startup probe ([`warmup.py`](docker/vllm/warmup.py)) отправляет настоящие запросы батчами 1, 2, 4 и 8, и трафик приходит на прогретый под. Кэш лежит в `/tmp`: он переживает рестарт контейнера, но не пересоздание пода.
- **Лимит памяти влияет на старт.** vLLM проверяет свободную часть лимита перед выделением KV-кэша, а `torch.compile` занимает память до этого. С лимитом 11 ГиБ и кэшем 4 ГиБ холодный старт падал, поэтому кэш уменьшен до 2 ГиБ. Этого достаточно: 74 880 токенов, или 9 запросов максимальной длины одновременно.

## Нагрузочное тестирование

Команда:

```bash
bash loadtest/run_experiment.sh baseline
```

Скрипт поднимает port-forward и запускает [`loadtest.py`](loadtest/loadtest.py). Тест замкнутый: N клиентов шлют запросы подряд. Каждый запрос генерирует ровно 64 токена (`ignore_eos`), у каждого промпта случайный префикс, чтобы кэш не искажал результат. Каждый сценарий сначала прогоняется без замера, иначе в цифры попадает компиляция Triton.

Стенд: Ryzen 5 7500F (6 ядер, AVX-512 BF16), Minikube в Docker Desktop на WSL2, лимит пода 8 CPU и 11 ГиБ. Сырые результаты: [`loadtest/results/`](loadtest/results).

Время указано в секундах. Ошибок нет ни в одном сценарии.

| Промпт | Токенов в промпте | Клиенты | Запросов | TTFT p50 | TTFT p95 | Latency p50 | Latency p95 | Запросов/с | Выходных токенов/с |
|---|---|---|---|---|---|---|---|---|---|
| Короткий | 70 | 1 | 4 | 0,26 | 0,27 | 5,01 | 5,03 | 0,20 | 12,8 |
| Короткий | 70 | 4 | 12 | 0,96 | 0,98 | 5,79 | 5,90 | 0,69 | 44,0 |
| Короткий | 70 | 8 | 24 | 1,75 | 1,81 | 7,06 | 7,08 | 1,13 | 72,6 |
| Длинный | 1160 | 1 | 3 | 3,59 | 3,64 | 8,36 | 8,63 | 0,12 | 7,6 |
| Длинный | 1160 | 4 | 8 | 10,09 | 14,76 | 19,88 | 23,86 | 0,20 | 12,8 |
| Длинный | 1160 | 8 | 16 | 15,53 | 27,84 | 33,77 | 46,82 | 0,24 | 15,1 |

Два вывода из таблицы:

- **Генерация хорошо масштабируется батчем.** Один шаг занимает 78 мс при 1 клиенте и 84 мс при 8, поэтому пропускная способность растёт в 5,7 раза почти без потери в скорости на клиента.
- **Узкое место длинных промптов в обработке контекста.** Она идёт со скоростью около 320 токенов/с, и пока обрабатывается один длинный промпт, генерация у остальных ждёт.

### Выбор конфигурации

Выходных токенов в секунду на коротких промптах:

| Вариант | 1 клиент | 4 клиента | 8 клиентов | TTFT, 1 клиент |
|---|---|---|---|---|
| **BF16, `torch.compile`, потоки `auto` (выбран)** | 12,8 | 44,0 | 72,6 | 0,26 |
| Без компиляции, `-O0` | 11,6 | 38,7 | 67,5 | 0,30 |
| Потоки `nobind`, `OMP_NUM_THREADS=6` | 12,9 | 45,7 | 75,3 | 0,26 |
| Квантизация AWQ 4-bit | 14,3 | 36,1 | 49,2 | 0,50 |

- **BF16, а не AWQ.** Квантизация быстрее только в одном потоке (+12%), но в батче из 8 запросов проигрывает 32%, а TTFT вдвое хуже. Для сервиса с параллельными запросами это невыгодно.
- **Компиляция включена.** Она даёт +7% и всё равно не убирает компилятор из образа, он нужен Triton. Цена: минута при старте и 0,9 ГиБ памяти.
- **`auto`, а не `nobind`.** `nobind` быстрее на 3,7%, но требует вручную задать число потоков под конкретный CPU. Манифест с `auto` работает на другой машине без правок.

### Что менять для роста Throughput

Цифры ниже получены скриптом `run_experiment.sh`, каждый параметр менялся отдельно. Результаты: [`loadtest/results/tuning/`](loadtest/results/tuning).

**А. Большой поток запросов с малым числом токенов**

Главный рычаг здесь `--max-num-seqs`, то есть размер батча. Шаг почти не дорожает с ростом батча, поэтому больше запросов за шаг даёт почти прямой рост пропускной способности.

| Параметр, 16 клиентов, короткие промпты | Токенов/с | TTFT p50 | Latency p50 |
|---|---|---|---|
| `--max-num-seqs 8` (текущее значение) | 73,2 | 8,46 | 13,95 |
| `--max-num-seqs 16` | **103,4** | **3,25** | **9,90** |
| `--stream-interval 8` | 72,3 | 8,49 | 14,00 |

Увеличение `--max-num-seqs` улучшило и пропускную способность (+41%), и задержку: запросы перестали стоять в очереди. Значение стоит поднимать до числа одновременных клиентов, пока хватает KV-кэша. При этом новую форму батча нужно добавить в `BATCH_SIZES` в [`warmup.py`](docker/vllm/warmup.py), иначе первый полный батч заплатит за компиляцию Triton: без прогрева TTFT p95 доходил до 49 секунд.

`--stream-interval` здесь ничего не дал: API-сервер не узкое место. `--max-num-batched-tokens` не ограничивает этот сценарий, 16 × 70 токенов намного меньше 2048. Остальной запас даёт CPU: больше ядер или дополнительные реплики, но это я не измерял.

**Б. Запросов меньше, но контекст огромный**

Всё решает, повторяется ли контекст между запросами.

| Параметр, 4 клиента, 2800 токенов | Токенов/с | TTFT p50 | Latency p50 | Latency p95 |
|---|---|---|---|---|
| Уникальный контекст, текущие настройки | 5,9 | 18,98 | 43,22 | 62,44 |
| Уникальный контекст, `--max-num-batched-tokens 8192` | 6,1 | 27,71 | 42,17 | 51,38 |
| Общий контекст, префиксный кэш включён | **34,0** | **2,17** | **7,49** | **7,63** |
| Общий контекст, `--no-enable-prefix-caching` | 5,9 | 19,09 | 43,10 | 62,11 |

- **Префиксный кэш дал рост в 5,8 раза**, когда у запросов общий контекст: один документ, системный промпт, история чата. Он включён по умолчанию, поэтому главное не отключать его и держать общую часть в начале промпта. Случайный префикс в начале, как в моём тесте с уникальным контекстом, полностью убивает эффект.
- **`--max-num-batched-tokens` почти не влияет на Throughput** (+3%): на CPU упор в скорость обработки контекста, а не в размер порции. Он меняет распределение задержки: p95 лучше на 18%, но типичный TTFT хуже на 46%. Выбирать значение стоит по тому, что важнее.
- **`VLLM_CPU_KVCACHE_SPACE` и `--max-model-len`** нужно поднимать вместе с размером контекста, иначе запросы будут вытесняться или получат отказ. В моих тестах кэша хватало (74 880 токенов), поэтому эффект вытеснения не измерялся.
- Для уникальных больших контекстов настройкой vLLM большого выигрыша получить не удалось. Здесь помогают только дополнительные ядра или реплики.

## Известные ограничения

- `secrets.env` превращается в обычный Kubernetes Secret, то есть base64 в etcd. Для продакшена нужно шифрование etcd или внешний менеджер секретов.
- Service имеет тип ClusterIP, TLS нет. Снаружи нужен Ingress с TLS, иначе Bearer-токен идёт открытым текстом.
- Фильтр логов защищает только stdout и stderr процессов vLLM. Сам `kubectl exec` остаётся доступным администратору кластера.
- `PersistentVolumeClaim` с `ReadWriteOnce` ограничивает Deployment одной репликой. Для масштабирования нужен том `ReadWriteMany` или предзагрузка на узлы.
- Влияние `zentorch` отдельно не измерялось: образ без него не собирался.
